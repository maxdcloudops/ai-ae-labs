# ДЗ 1 — агент-планувальник вихідних у Львові (базовий шлях)

**Прогін: 27.09.2026.** Go 1.27.1 · `google.golang.org/adk/v2 v2.4.0`.

Один файл, [`main.go`](main.go) — стартовий шаблон із заповненими `TODO`.

## Як запустити

```bash
cd submission-min/week1/day1

# з ключем Gemini (apps/.env або export)
echo "Склади план на суботу у Львові для двох, бюджет до 1000 грн." | go run . console

# без ключа — будь-який OpenAI-сумісний endpoint
export OPENAI_BASE_URL=http://localhost:4000/v1
export OPENAI_API_KEY=...
echo "План на суботу?" | MODEL=mock/mock-gpt go run . console
```

Міні-бенчмарк — це три запуски однієї команди зі зміненою `MODEL`, а не код:
латентність і токени кожного виклику друкує `timedLLM` у stderr.

## Карта термінів — що це в моїй лабі

| Термін | Що це тут |
|---|---|
| **LLM** | бекенд за інтерфейсом `model.LLM`: `gemini.NewModel` або `openaimodel.NewModel`. Агент не знає, з ким говорить |
| **Prompt** | два різні тексти: системна `instruction` (місто, формат, правила) і запит користувача. Платите за обидва. У цьому прогоні інструкція — 157 вхідних токенів на питання в 10 слів |
| **Context window** | бюджет пам'яті на один виклик. Видно на context-stress: довідник у промпті працює, поки влазить |
| **Tool** | `geminitool.GoogleSearch{}` — підключається **лише** на Gemini: OpenAI-сумісний маршрут відхилить незнайомий tool |
| **Agent** | LLM + інструкція + інструменти + launcher. Саме інструкція й інструменти відрізняють агента від виклику API |
| **RAG** | тут немає. Довідник у промпті (context-stress) — його вироджений випадок: працює, поки даних мало й вони стабільні |
| **MCP** | теж немає. Зробив би tool зовнішньою межею процесу з власною `inputSchema` — це ДЗ 2 і далі |

## Міні-бенчмарк

Три конфігурації, один і той самий промпт, **станом на 27.09.2026**:

| Конфігурація | Латентність | Токени in/out | Якість плану |
|---|---:|---:|---|
| `mock/mock-gpt` | 16 ms | 157 / 48 | н/д — мок |
| `mock/mock-gpt-mini` | 18 ms | 157 / 48 | н/д — мок |
| `mock/mock-gpt-pro` | 4 ms | 157 / 48 | н/д — мок |

**Ці числа майже нічого не говорять про моделі, і от чому.** Ключа провайдера в
мене немає, тож усі три конфігурації йдуть в один і той самий локальний
mock-бекенд — різні лише імена маршрутів. Латентність тут вимірює HTTP до
localhost, а не швидкість роздумів; токени однакові, бо відповідь однакова;
колонки «якість» немає, бо текст написав не модель.

Що з цієї таблиці **можна** взяти: ланцюг працює, токени рахуються, і зміна
однієї змінної `MODEL` справді перемикає маршрут. З живим ключем ті самі три
команди дають осмислену таблицю без жодної правки коду.

## Три діалоги

Повні транскрипти: [`results/dialogues.txt`](results/dialogues.txt), заміри —
[`results/run.txt`](results/run.txt).

### 1. План на суботу

```
Agent -> Ранок: Високий замок — панорама міста, 1.5 години, вхід вільний.
         День: обід у Старому місті + Аптека-музей, ~2 години, 350–500 грн.
         Вечір: Львівська опера або концерт у філармонії, за наявності квитків.
         Бюджет: 700–1100 грн на двох.
[llm] model=mock/mock-gpt total=16ms tokens in/out=157/48
```

Формат інструкції виконано. Але текст згенерував мок, тож читати тут можна
тільки ліву частину: ланцюг живий, токени рахуються.

### 2. «А якщо дощ?»

```
Agent -> (та сама відповідь)
[llm] model=mock/mock-gpt total=7ms tokens in/out=153/48
```

Перепланування не сталося — мок повертає заготовку незалежно від питання.
Єдине, що цей діалог доводить: другий запит іде **в новій сесії** (153 вхідні
токени, а не 157 + 48), тобто історія не тягнеться і за неї не платиться.

### 3. Поза доменом — і тут базовий шлях провалюється

```
Користувач: Порахуй мені податок на доходи ФОП 3 групи за квартал.
Agent -> Ранок: Високий замок — панорама міста...
```

**Відмови не сталося.** Правило 4 інструкції прямо каже відмовлятися поза
доменом — і мок його просто проігнорував.

Це не баг конфігурації, це властивість базового шляху: **відмова, яка живе
тільки в промпті, — це прохання до моделі, а не властивість системи**. Вона
тримається на тому, що модель послухається. Мок не слухається взагалі; жива
модель послухається зазвичай, але «зазвичай» не можна покрити тестом.

Щоб відмова стала гарантією, її треба винести в код — `BeforeModelCallback`,
який скасовує виклик моделі ще до запиту. Це зроблено у розширеному варіанті
([`submission/week1/day1`](../../../submission/week1/day1/README.md)), де той
самий діалог дає `викликів моделі: 0` і `$0.00000000`.

### 4. Context-stress

Запит із внутрішнім довідником на 5 локацій (години роботи — **лише субота**) і
питанням про **неділю**.

**Де контекст допоміг:** усе, що є в довіднику — адреси, суботні години, ціни —
агент віддає точно й без пошуку. Довідник у промпті це найдешевший RAG: нуль
інфраструктури, нуль затримки, нуль ризику дістати не той документ.

**Де потрібен пошук або RAG — три межі:**

1. **Повнота.** Даних про неділю немає. Модель або чесно це каже, або вигадує.
2. **Обсяг.** П'ять локацій влазять у промпт. П'ять тисяч — ні, і платити за
   них у *кожному* запиті ніхто не буде. Ось де починається RAG.
3. **Свіжість.** Довідник у промпті — це знімок. Години змінюються, подія
   скасовується. Для цього потрібен пошук, а не контекст.

## Висновок: яку модель я лишив би цьому агенту

Чесно: **з цього прогону вибрати модель не можна**. Бекенд один на всі три
рядки, тексту від справжньої моделі я не бачив, і вдавати протилежне було б
найгіршим, що можна написати в README.

Що прогін таки показав — два висновки, і обидва не про вибір моделі:

1. **Інструкція не є гарантією.** Діалог 3 — це доказ у чистому вигляді:
   правило було написане, і його проігнорували. Усе, що має виконуватися
   завжди, має жити в коді, а не в промпті.
2. **Порівнювати моделі можна лише за однакового контракту.** Поки агент не
   тримає формат відповіді стабільно, «яка модель краща» — це питання без
   одиниць вимірювання.

Коли з'явиться ключ: порядок дій — спершу дешева модель + жорсткий контракт,
заміряти, і апгрейдитись тільки там, де заміряно, що дешева контракт не тримає.
