## Чому валідатор власний: `kubectl --dry-run=client` не валідує

Перше, що я зробив, — перевірив очевидний інструмент. Він не працює:

```console
$ cat bad.yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: pay-api}
spec:
  replicas: "two"          # рядок замість числа
  ...
      containers:
        - name: api
          image: pay-api:1.2.3
          bogusField: nope  # вигадане поле

$ kubectl apply --dry-run=client -f bad.yaml
deployment.apps/pay-api created (dry run)        # ← ПРИЙНЯВ

$ kubectl apply --dry-run=client --validate=strict -f bad.yaml
deployment.apps/pay-api created (dry run)        # ← І ТУТ ПРИЙНЯВ
```

Клієнтську валідацію з kubectl прибрали; `--validate=strict` потребує живого
API-сервера для OpenAPI-схеми. Перевірено на kubectl v1.34.1, 11/2026.
`kubeconform` зробив би це, але лаба, яка проходить лише коли встановлено
додатковий бінарник, — це лаба, що падає на машині рецензента (AGENTS.md §5.3).

Тому [`internal/manifest`](../../../week6/Day11_Dynamic_Workflows_Multi_Critic/labs11/internal/manifest/manifest.go)
перевіряє **тільки те, що обʼєктивно**: API-сервер відхилив би маніфест, або
навантаження провально не запуститься.

| Правило | Чому обʼєктивне |
|---|---|
| YAML розбирається, дубльованих ключів немає | дубль ключа тихо змінює сенс замість падіння |
| `kind` + `apiVersion` з відомої пари | «якийсь інший kind, мабуть норм» не є результатом валідації |
| `metadata.name` — DNS-1123 | API-сервер відхилить |
| `spec.replicas` — ціле число | `replicas: "two"` — рівно те, що kubectl пропускає |
| `selector.matchLabels` ⊆ `template.metadata.labels` | API-сервер відхилить Deployment |
| образ має явний тег або digest, не `latest` | два поди одного ReplicaSet можуть бути різним кодом |
| імена контейнерів не повторюються | API-сервер відхилить |

Усе, про що можна спорити — чи щедрий ліміт, чи добре налаштована проба, — тут
**не перевіряється**. Це робота LLM-критика, і межа проведена свідомо.

## п.1 — Цикл

```
Start → multi_critic_loop (dynamic)
          ├─ maker (AgentNode, RunNode WithUseSubBranch)
          ├─ валідатор (чиста функція, БЕЗ моделі)
          └─ critic_panel (підграф: fan-out 3 критики → JoinNode)
```

**Валідатор першим, і це не стилістика.** Маніфест, який не розбирається,
неможливо судити за привілеями, а платити трьом моделям за опис безпеки файлу
з YAML-помилкою — найдешевший спосіб спалити бюджет. Закріплено
`TestGateRunsBeforeCritics`: при maker'і, який ніколи не віддає валідний
маніфест, критиків викликають **нуль** разів.

**Ліміт перевіряється ПЕРЕД викликом maker'а.** Після виклику бюджет уже
витрачено на крок, який ми вирішили не робити. Той самий висновок, що в ДЗ 7.

**Фідбек — сирий вивід інструмента.** `[validator] ` + повідомлення валідатора,
без переказу: maker виправляє те, що сказав інструмент.

**Коментарі ВСІХ критиків ідуть у фідбек**, а не першого. Якби збирався лише
перший, maker виправив би один клас проблем із трьох і наступні спроби пішли б
на те, що вже було відомо. Закріплено `TestCriticFeedbackReachesTheMaker`:
у журналі мусять бути зауваження про `runAsNonRoot`, `resources` і
`LEDGER_PASSWORD` одночасно.

**Чого я не мав на початку.** Ні `Reference`, ні «майже правильний» варіант не
проходять через відмову панелі — обидва чисті за безпекою. Тобто шлях
«критики → фідбек → виправлення» у демонстрації не було видно взагалі, хоча
саме він і є п.1. Довелося додати третій варіант (`-maker insecure`), який
проходить валідатор і падає на критиках.

## п.2 — Чотири критики, один обʼєктивний

| Критик | Фокус | Хто судить |
|---|---|---|
| **валідатор** | схема, типи, селектор, теги образів | **код** |
| `privileges` | `runAsNonRoot`, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`, `drop: [ALL]`, `privileged` | LLM |
| `limits` | `requests` і `limits` на cpu й memory у КОЖНОГО контейнера | LLM |
| `secrets` | секрети відкритим текстом у `env[].value`; `secretKeyRef` без явного `optional` | LLM |

Кожен — `llmagent` із власною інструкцією, своїм вузлом і типізованим
`Verdict{Critic, Passed, Comments}` із заповненим `Critic`.

**Кворум одностайний: кожен критик мусить пройти.** Голосування тут було б
помилкою — фокуси не перетинаються, тому чистий вердикт про привілеї нічого не
каже про відсутні ліміти памʼяті, і два «так» не можуть перебити одне «ні»
(`TestQuorumIsUnanimous`).

**Критик не має права писати про чужий фокус** — закріплено
`TestCriticRulesStayInTheirLane`. Інакше панель тричі повідомляє про одне й те
саме, а про щось інше — жодного разу.

### Про `secretKeyRef` без `optional: true`

Умова формулює правило як «наявність `env.valueFrom.secretKeyRef` **без**
`optional: true`». Я реалізував іншу вимогу й кажу про це прямо: `optional:
true` означає «запустись без секрету», тобто под підніметься зламаним і тихо.
Тому критик вимагає **оголосити намір явно** — будь-яке значення `optional`,
але присутнє. Якщо ментор читає умову буквально, це місце для дискусії; мовчки
реалізувати вимогу, яка робить систему гіршою, я не став.

### Офлайн-критики — правила, а не скрипт

Без провайдера кожен критик — своя функція-правило, обгорнута в `model.LLM`.
Це не записаний сценарій: той самий критик на іншому маніфесті дає інший
вердикт (`TestOfflineCriticJudgesRatherThanReplays`). Інакше офлайн-панель
«знаходила» б проблеми, виписані заздалегідь, і eval-таблиця не означала б
нічого.

Та сама функція — і written-down визначення того, що просять у живого критика:
інструкція — та сама політика словами.

## п.3 — Валідація вердиктів

Чотири малформації, чотири сентинели, перевірка через `errors.Is`:

| Що прийшло | Сентинел |
|---|---|
| проза замість JSON | `ErrVerdictUnreadable` |
| роль, якої немає в панелі | `ErrVerdictUnknownCritic` |
| `critic` не збігається з вузлом (або порожній) | `ErrVerdictRoleMismatch` |
| `passed=false` без коментарів | `ErrVerdictSilentFailure` |
| `passed=true` з коментарями | `ErrVerdictContradiction` |

Нічого не «ремонтується». Вердикт, що не задовольняє власний контракт, —
це свідчення про критика, а не про маніфест.

**Fail-closed:** відкинутий або відсутній вердикт НІКОЛИ не дає прийняття
(`TestAggregateFailsClosed`). Інакше найдешевший спосіб пройти панель — зламати
критика.

**Правило двох помилок.** Умова дозволяє або «зупинити цикл», або «вважати
`Passed=false` із системним коментарем». Я зробив обидва, за різних умов:
перший невалідний вердикт — відмова, цикл продовжується (один збій флакучого
критика не має вбивати ран, який ще може зійтись); **другий від тієї самої
ролі** — `ErrCriticBroken` і зупинка, бо це вже факт про критика, і далі
крутити цикл означає спалити бюджет на нього.

### Чому `OutputSchema` НЕ підключена

Стартер підказує `llmagent.OutputSchema`. Я її не підключив, і це свідоме
рішення з ціною.

З `OutputSchema` ADK валідує й розбирає відповідь сам, вихід вузла стає
обʼєктом, а відповідь-проза **не доходить до мого коду**: вона падає всередині
вузла типізованою помилкою, яка не називає, який критик зіпсував. Це знімає
рівно ОДНУ з чотирьох малформацій і забирає можливість обробити решту як те,
чим вони є — відмовою названого критика, із записом у журнал і продовженням
циклу.

Схема лишилась у коді як оголошений контракт (`VerdictSchema`) — і головне:
**схема не зробила б валідацію непотрібною.**
`{"critic":"limits","passed":true,"comments":["немає limits"]}` задовольняє
схему повністю і лишається самосуперечливою нісенітницею.

## п.4 — Eval-звіт: головна цифра — false accepts

`maxAttempts: 4`, три завдання, чотири профілі maker'а. Три рани на різних
задачах — рядки таблиці; чотири профілі — щоб цифру можна було **перевірити**,
а не брати на віру.

**`-maker buggy`** — маніфест, що задовольняє кожне показане правило й ламає
приховане:

| завдання | прийнято | спроб | токени | holdout | примітка |
|---|---|---:|---:|---|---|
| `pay_api_deployment` | так | 2 | 4807 | **ПРОВАЛ** | `grace_period`, `liveness_after_readiness` |
| `ledger_cronjob` | так | 2 | 4413 | **ПРОВАЛ** | `concurrency_forbid`, `history_limits` |
| `pay_api_service` | так | 2 | 3090 | **ПРОВАЛ** | `target_port_named` |

**ХИБНИХ ПРИЙНЯТТІВ: 3 із 3.**

**`-maker insecure`** — спершу падає на критиках, потім виправляється:

| завдання | прийнято | спроб | токени | holdout |
|---|---|---:|---:|---|
| `pay_api_deployment` | так | 3 | 9558 | пройдено |
| `ledger_cronjob` | так | 3 | 8854 | пройдено |
| `pay_api_service` | так | 2 | 3090 | **ПРОВАЛ** |

**ХИБНИХ ПРИЙНЯТТІВ: 1 із 3.**

**`-maker reference`** — 0 із 3, holdout пройдено всюди.
**`-maker stub`** — нічого не прийнято, 4 спроби, `бюджет вичерпано`.

### Що ця цифра означає

3 із 3 — не поломка harness-а, а результат. Панель перевірила все, за що
відповідає (привілеї, ліміти, секрети), і жодне з прихованих правил не входить
у її зону: час на дренаж запиту, порядок проб, `concurrencyPolicy`, іменований
`targetPort`. **Панель критиків ловить рівно те, за що хтось відповідає.**

І найцікавіший рядок — `pay_api_service` у профілі `insecure`: 1 із 3. Service
не має пода, тому критики привілеїв, лімітів і секретів проходять **тривіально**
(`TestServiceLeavesTheCriticsNothingToSay`). Панель із трьох голосів тихо стає
панеллю з нуля, і цифра це показує.

Практичний висновок, і він не про промпт: щоб false accepts упали, потрібен
критик, який **володіє** цим класом правил. Кращий промпт для наявних трьох не
допоможе — вони й так відповідають правильно на своє питання.

### Токени

`internal/usage.Meter` рахує за `UsageMetadata` по авторах:

```

privileges                    2     2248      106
```

## п.5 — Event log

Зріз вище (п.1) — реальний вивід `-trace`. У ньому видно:

- **кожну ітерацію** maker'а (рядки 0, 2, 13);
- **кожен вердикт** — і сирий JSON від критика, і рядок `[verdict]` із
  розібраними полями;
- **рішення гейта на кожній спробі** під ключами
  `w6p1:attempt:1=gate:parse`, `w6p1:attempt:2=gate:ok`, `…=panel:…`,
  `w6p1:attempt:3=accepted`;
- фінальний `[loop_done]`, а в профілі `stub` — `[budget_exhausted]`.

Три виклики критиків (4–6) стоять **до** будь-якого `[verdict]` — панель
справді паралельна.

**Лічильники звіту виводяться з журналу**, а не з окремої структури, у яку
пише цикл (`statsFromEvents`). Та сама причина, що з журналом аудиту ДЗ 9:
якщо потік подій не є достатнім записом того, що сталося, то «event log
показує траєкторію» — речення, а не властивість.

Подія ніколи не несе `ev.Output`: виконання вузла може мати рівно один вихід, і
вихід цього вузла — його return. Інакше ран падає з «only one event per
execution can carry output».

## ++ Advanced

**Паралельні критики.** Панель — `fan-out` у **статично оголошеному підграфі**
(`workflow.NewWorkflowNode("critic_panel", …)` з `AddFanOut` + `JoinNode`),
який цикл викликає через `RunNode(ctx, panel, d, workflow.WithUseSubBranch())`.
Саме так, як вимагає умова: `JoinNode` — у статичному підграфі, а не всередині
динамічного вузла.

Замір (`TestCriticsRunConcurrently`):

```
три критики по 150ms: панель паралельно 160ms, послідовно було б ≈450ms
```

**Замір синтетичний, і це сказано в тесті.** Офлайн-критики — чисті функції й
відповідають за мікросекунди: перекривати нічого. Затримка 150 мс імітує
провайдера. Поріг у тесті — «менше послідовного», а не «рівно втричі»: на
завантаженій машині й за реальних лімітів провайдера точного множника не буде.

**Табличні тести без моделі.** `TestVerdictValidationBySentinel` (шість
малформацій через `errors.Is`), `TestParseVerdict_Contract` (контракт
стартера), `TestAggregateFailsClosed`, `TestSchemaErrorPaths` (20 рядків
помилок валідатора) — усе без LLM і без мережі.

**Per-node таймаут.** `NodeConfig{Timeout: loopTimeout()}` на вузлі циклу,
і він **більший** за суму того, що всередині (`attempts × 90s`). Таймаут
вузла, менший за дитячі, перетворює повільного провайдера на незрозумілий
частковий збій.

## Суперечність у стартері

`main_test.go` стартера містить кейс, який суперечить умові:

```go
{
    name: "чистий JSON проходить",
    raw:  `{"critic":"correctness","passed":true,"comments":["ок"]}`,
},  // очікує УСПІХ
```

А п.3 умови прямо вимагає відсікати «`Passed=true` з непустими `Comments`».
Я тримаюсь умови — за нею виставляють бали, і вердикт, дві половини якого не
узгоджені, справді не є свідченням. Кейс змінено на очікування помилки, з
коментарем у коді. Там же `role` переведено з `correctness` на `limits`:
у альтернативній темі панель інша.

Також довелось уточнити формулювання власних сентинелів, щоб вони містили
підрядки, які перевіряє контракт стартера («JSON», «роль»).

## Межі

- **Провайдера немає.** Критики офлайн — правила, не модель. Топологію графа,
  порядок перевірок, валідацію вердиктів, кворум і бюджет це перевіряє
  повністю; **якість суджень LLM — ні**. Умова просить «різні system prompts»
  — вони написані й перевіряються лише на компільованість.
- **Токени синтетичні** (`usage.Estimating`), thinking-токенів немає.
- **Замір паралельності синтетичний** (затримка 150 мс).
- **`-task … web webui api`** (Web UI лаунчера) не перевіряв на :8080.
- **🔥 Бонус-трек не робив** (`critic_static_analysis`: для k8s-теми це був би
  четвертий вузол із `kubeconform`, якого немає в оточенні).
